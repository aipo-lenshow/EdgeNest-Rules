# edgenest-rules

EdgeNest 客户端的路由规则数据。改这里,用户当天就能拿到,不用等客户端发新版。

English: [README.md](./README.md)

## 这个仓库怎么运作

```
main 分支(默认)          sources/ai_core.json      ← 规则数据的源,要改就改这里
                          sources/streaming.json
                          …一个包一个文件,共 16 个
                                  ↓  推送后 CI 自动组装
rule-set 分支             catalog.json              ← 成品,只有这一个文件
                                  ↓  客户端拉取
用户设备                  规则生效
```

**数据在两个地方,别找错:**

- 你要**编辑**的是 `main` 分支的 `sources/` 目录(仓库首页就能看到)
- 客户端**下载**的是 `rule-set` 分支上的 `catalog.json`(要在 GitHub 上切换分支才看得到)。它是 CI 生成的,不要手工改 —— 下次构建会覆盖

## 规则内容从哪来

**大部分包每天自动跟上游对齐**,不靠人工维护。每个这样的包声明它跟随哪些上游分类,再加上我们自己的覆盖层:

```jsonc
"upstream": ["openai", "anthropic"],   // 每天跟随
"add":      { "suffixes": [...] },     // 我们要、上游没有的
"exclude":  ["klingai.com"],           // 上游有、我们不要的
"suffixes": [...]                      // 自动生成,不要手改
```

    包内容 = 上游分类 ∪ add − exclude

上游是 [v2fly/domain-list-community](https://github.com/v2fly/domain-list-community)(MIT),社区按服务切好的分类,每天都在动。跟随它才不会出现「域名早死了没人发现」—— 我们 AI 包里的 `bard.google.com` 就这么躺了好几个月。

**三家大厂刻意保持手工**:上游的 `apple`(1807 条)、`google`(1082 条)、`microsoft`(753 条)覆盖的是这家厂商的全部域名,含国内接入点。我们的包只是用户真正会想到的那几个服务,跟随这些分类会让 16 条的包涨到上千条,并改变它的走向。

`regexp:` 类型的条目在导入时丢弃 —— 客户端没有正则匹配器,一条被静默忽略的规则比没有这条更糟。同步脚本会报告丢弃了多少条。

## 改一条规则要做什么

1. 手工包:直接编辑 `sources/<包名>.json` 的 `suffixes`;**跟随上游的包:改它的 `add` / `exclude`,不要改 `suffixes`**(下次同步会覆盖)
2. 提交到 `main`
3. CI 自动跑:校验 → 生成 `catalog.json` → 推到 `rule-set` 分支(约一分钟)
4. 用户侧:**连上节点时自动检查,12 小时内不重复**;也可以在客户端「内置规则包」页面点「立即更新」立刻拉取

新数据在**下次启动核心时生效**(重新连接一次)。

推送到 `main` 只发布你写的东西 —— **push 不跑上游同步**,你的改动不会跟上游一夜之间的变化混在一起。

## 每天自动跑什么,以及刹车

03:00 UTC:跟上游同步 → 构建 → **检查这次差异是否正常** → 发布。内容没变就不发布。

`scripts/guard_changes.py` 是刹车。每天无人值守地改所有人的路由,必须有个拦得住的东西:上游一次误删(某个分类被清空、合并时丢了一半)否则会在当天静默同步到每台设备。出现下面任一情况时,**不发布**,改为开一个 issue 把差异贴出来:

- 某个包减少超过 25 条,或减少超过自身的 30%
- 某个包变空或消失
- 整个目录一次涨到 3 倍以上

阈值判断的是**形状**不是对错 —— 没有脚本能判断对错。手动触发(`workflow_dispatch`)等于人说「我看过了」,会无视阈值直接发布。

## 一个包长什么样

```jsonc
{
  "id": "ai_core",              // 必须和文件名一致
  "nameZh": "AI 核心对话",
  "nameEn": "AI chat (core)",
  "descZh": "…",
  "descEn": "…",
  "defaultOutbound": "proxy",   // "proxy"(走代理)| "direct"(直连)
  "defaultOn": true,            // 用户首次安装时这个包是否默认开启
  "suffixes": ["openai.com"],   // 域名后缀,匹配它和它的所有子域
  "keywords": ["openai"]        // 关键词,匹配域名里包含这段字符的
}
```

**为什么发域名清单而不是编译好的规则集文件**:客户端允许用户把包里的**某一条域名**单独改成别的出站,这需要拿到条目本身;编译产物拆不回来。

## 本地验证

```bash
python3 scripts/build_catalog.py --out dist/catalog.json
```

改错了会**在这一步失败**,不会发布出去,更不会到用户设备上:

- 必填字段缺失
- `id` 和文件名对不上
- 包里一条规则都没有
- **同一个域名出现在两个默认出站不同的包里** —— 客户端按出站合并规则,这种情况匹配结果不确定

## 域名复核

`scripts/check_domains.py` 会报告**已经解析不到的域名**,CI 每天跑,结果汇总在一个固定的 issue 里。

**这是提示你去看一眼,不是让你删。** 一个域名可能在某个网络解析不到、在另一个网络完全正常。

也要知道它**抓不到什么**:服务早就停了、但域名还在解析的情况,它一条也发现不了(`bard.google.com` 就是这样)。这类只能靠人工发现。脚本开头写明了这个边界。

## 规则怎么分类

按**用户在做什么**分,不按厂商分 —— AI 对话、开发者基础设施、知识与学术、流媒体。名称和描述保持中性,描述的是这一组流量是什么。新增包也照这个来。
